# Installation

Step-by-step self-hosted installation guide for Socly.

## Requirements

| Component | Version / notes |
|-----------|-----------------|
| PHP | 8.2+ with `pdo_mysql`, `openssl`, `mbstring`, `json`, `fileinfo` |
| Database | MariaDB 10.4+ / MySQL 8+ (`utf8mb4`) |
| Web server | Apache 2.4+ with `mod_rewrite`, or Nginx + PHP-FPM |
| Composer | 2.x (install and updates only) |
| Permissions | `storage/` and `.env` writable by the web server user |
| HTTPS | recommended (`Secure` session cookie, HSTS) |

OCR is **optional**; it is only needed to prefill the statute and privacy notice from RUNTS PDFs:

```bash
sudo apt install poppler-utils tesseract-ocr tesseract-ocr-ita
```

`exec()` must be enabled in PHP and the `php` CLI binary must be available (the OCR worker starts in
the background via `nohup`). When `exec()` is disabled, Socly falls back to a short inline OCR and
warns in the UI when the extracted text is partial.

## One-click installation (Linux, macOS, Windows)

The scripts in `bin/install/` verify the environment, install PHP 8.4/8.3 (preferred) or 8.2 with
the required extensions, MariaDB/MySQL, Composer and optional OCR tools, create the database and
`.env`, apply migrations and start the local server:

```bash
sudo bash bin/install/linux.sh                                      # Linux
bash bin/install/macos.sh                                           # macOS (Homebrew)
powershell -ExecutionPolicy Bypass -File bin\install\windows.ps1    # Windows (admin)
```

Useful flags: `--check` (verify only), `--plan` (show actions without changes), `--no-ocr`,
`--no-serve`, `--port=8080`, `--db-root-pass=...`, `--user=<system user>` (owner of
`.env`/`storage/`; use it when installing as root on a host served by `www-data`),
`--reset-db-pass` (rotate the password of an already existing DB user: without it an account with
the same name but a different password stops the installation instead of being overwritten),
`--force` (overwrite an `.env` that points to another database). On Windows the parameters are
`-Check` (with `-Json` and `-ReportPath` for a machine-readable report), `-Plan`, `-Ocr`, `-NoOcr`,
`-NoServe`, `-Port`, `-DbRootPass`, `-ResetDbPass`, `-Force`, `-Uninstall`, `-PurgeDatabase`,
`-PurgeMariaDb`. Details in [`bin/install/README.md`](../bin/install/README.md).

The scripts **never touch an existing installation**: PHP and the MariaDB server are installed only
when missing (a host already managed by Plesk/cPanel or with a complete PHP stack does not get a
second one), an `.env` pointing to another database is not rewritten and the password of a
pre-existing MySQL user is never changed. On a shared server install into a new folder with a
dedicated database and user.

Then open `http://127.0.0.1:8080/install` and complete the wizard (association, period/type, fields).
Then sign in as `admin@socly.it` (maintenance password defined in code, never printed by the scripts)
and complete the first-run **setup** at `/setup`, which creates the association **Admin** account.
The built-in PHP server is for installation and evaluation: for production use Apache/Nginx + HTTPS
as described below.

`/install` only handles the **infrastructure**: database credentials, creating the DB when missing,
migrations and `storage/installed.lock`. When the one-click installers already wrote `.env` and
created the database, the page asks nothing: it locks the installation and opens the **guided setup**
(`/setup`) directly, with the maintenance session already active (no login form). The wizard collects
language, association data and seat, logo and colors, officers, statute and privacy, member types and
periods, profile fields, treasury accounts, mail, enrollment, components, Admin account and consents.
Until the association **Admin** exists the wizard is the only way in: `/login` shows no credential
form, just the button that reopens the configuration (“Resume setup” once some steps are saved).
“Exit and continue later” saves and suspends — coming back resumes at the first pending step —
while “Discard everything” wipes the progress and reopens the wizard at step 1. As soon as the Admin
exists (last wizard step) or every step is done, the maintenance account `admin@socly.it` is required.
`/install` is only needed again to restore the database credentials when the instance cannot connect
anymore.

## 1. Get the code

```bash
git clone https://github.com/dadaloop82/socly_public.git socly
cd socly
composer install --no-dev --optimize-autoloader
cp .env.example .env
```

Set at least `APP_URL` and the `DB_*` values in `.env` (or let the wizard write them).
`APP_KEY` is generated by the installer: **keep it with your backups**, otherwise encrypted settings
cannot be decrypted.

## 2. Database

Create the database and user (the installer can create the database itself when the user has the
`CREATE` privilege):

```sql
CREATE DATABASE socly CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'socly'@'localhost' IDENTIFIED BY 'a-long-password';
GRANT ALL PRIVILEGES ON socly.* TO 'socly'@'localhost';
FLUSH PRIVILEGES;
```

Migrations (`database/migrations/`) run automatically on first boot and after every update: no manual
command is required.

## 3. Permissions

```bash
# adapt the user to your system: www-data (Debian/Ubuntu), apache, nginx…
sudo chown -R www-data:www-data storage
sudo find storage -type d -exec chmod 775 {} \;
sudo chown www-data:www-data .env
```

The document root must point to `public/` **only**. `.env`, `storage/` and `vendor/` stay outside.

## 4. Web server

**Apache** (`a2enmod rewrite`, `AllowOverride All`):

```apache
<VirtualHost *:443>
    ServerName socly.example.org
    DocumentRoot /var/www/socly/public
    <Directory /var/www/socly/public>
        AllowOverride All
        Require all granted
    </Directory>
</VirtualHost>
```

**Nginx + PHP-FPM**:

```nginx
server {
    listen 443 ssl;
    server_name socly.example.org;
    root /var/www/socly/public;
    index index.php;

    location / { try_files $uri $uri/ /index.php?$query_string; }
    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
    }
    location ~ /\.(?!well-known) { deny all; }
}
```

`public/.user.ini` raises upload limits to 25 MB for PDFs. With Nginx + PHP-FPM also check
`upload_max_filesize` / `post_max_size` in `php.ini`.

## 5. Guided installation

Open `https://socly.example.org/install` and complete the five steps:

1. **Database and URL** — MySQL credentials and the public application URL.
2. **Association** — name, contacts, brand colours, default locale, GDPR.
3. **Membership period and type** — label, dates, name and price of the member type.
4. **Profile fields** — default fields to enable and the required ones.
5. **Summary** — confirm: tables, permissions and `storage/installed.lock` are created.

The **maintenance account** (the only SuperAdmin, `admin@socly.it`) is hardcoded in the application:
it is not created by the wizard, cannot be edited or deleted from the UI, and no other user can be
promoted to SuperAdmin. The password is stored only as an Argon2id hash in
`app/Support/PlatformMasterAccess.php`. After installation sign in with that account and complete the
**first-run wizard** at `/setup`: it creates the association **Admin** account and guides the
configuration (association data, RUNTS or website lookup, logo and colours, statute and privacy
notice, treasury and deadlines). Setup is not anonymous: without the maintenance login nobody can
create the association Admin.

## 6. Verify

- `https://socly.example.org/login` responds and login works.
- Dashboard, member creation and payment update work.
- If you use OCR, check the diagnostics:

```bash
php -r 'require "vendor/autoload.php"; print_r((new Socly\Services\PdfTextExtractor())->ocrDiagnostics());'
```

Useful logs: `storage/logs/app.log`, `storage/cache/runts_ocr_job.log`,
`storage/cache/runts_ocr_last.json`.

## 7. Updates

Installed instances read the public `latest.json` manifest and notify administrators when a new
version is published. Manual update:

1. Back up the database, `.env` and `storage/`.
2. Download the latest release from `dadaloop82/socly_public` (branch `main` or ZIP).
3. Replace application files, keeping `.env`, `.env.user` and `storage/`.
4. Run `composer install --no-dev` if dependencies changed.
5. Open the site: pending migrations run on the first request.

### One-click / automatic update (git checkouts)

Where the app is a **git checkout** whose `origin` remote is readable by the PHP/CLI user, the update
is available out of the box (no `.env` flag required; set `UPDATE_ENABLED=false` to disable it):

- inside the app: sidebar card “Update available” → **Update** (confirmation required);
- from the command line: `php bin/update.php` (only checks) or `php bin/update.php --apply`
  (backup + git fetch + fast-forward + migrations, same engine as the button);
- scheduled (nightly, fully automatic):

  ```cron
  15 4 * * * php /path/to/socly/bin/update.php --apply >> /path/to/socly/storage/logs/update.log 2>&1
  ```

Both paths refuse to run on temporary demo instances, when `UPDATE_ENABLED` is false and when the
working tree has local modifications (`updates.dirty`). The login page always shows the installed
version and, through “Check for updates”, the published/remote version with the release notes.

`UPDATE_REPO` only feeds the “last commit” line in the UI: fetch and merge always use the checkout’s
own `origin` remote, so an installation cloned from the public repository updates with no SSH key
(anonymous HTTPS read). ZIP installations have no git metadata and must use the manual procedure above.

### Backup, verification and automatic rollback

Before changing anything the updater writes a snapshot to `storage/backups/update-<date>-v<version>/`:

- `code-<commit>.tar.gz` — the previous application code (`git archive`);
- `database.sql` — a full database dump (`mysqldump`; when the binary/config is missing the update
  proceeds but reports that only the code could be restored);
- `update.json` — from-version, from-commit, timestamp and backup outcome.

After the fast-forward it verifies that the version actually changed, that the database answers and
that no migration file is left pending. If verification (or any step) fails, the previous commit is
restored with `git reset --hard` and, when available, the database dump is reloaded before reporting
the failure. The outcome is shown in the UI flash, printed by `bin/update.php` and written to the
audit log (`update.applied`, `update.rolled_back`, `update.failed`).

## Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| Immediate 500 error | `storage/` permissions or `.env` not writable; check `storage/logs/app.log` |
| “DB error” in the wizard | Wrong credentials or missing database; reopen `/install` (step 1) to fix them |
| OCR unavailable | `exec()` disabled, or missing `pdftoppm`/`tesseract`/Italian `tessdata` |
| OCR very slow | Normal for long scanned PDFs: the worker reads every page (up to 30 minutes) |
| PDF upload rejected | 25 MB limit (`public/.user.ini`) or `php.ini` `post_max_size` |
| Migrations failed | The DB user must be allowed to create/alter tables and indexes |
